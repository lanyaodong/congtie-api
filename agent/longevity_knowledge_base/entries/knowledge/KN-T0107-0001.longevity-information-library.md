# 长寿信息库是什么

## 1. One-line Summary

长寿信息库是 Congtie 持续整理、审核和更新的通用长寿信息外脑，为人类用户和 AI Agents 提供来自全球范围、可复用、证据与使用边界清晰且经过人工治理的长寿信息上下文。

## 2. User-facing Explanation

与健康寿命相关的信息分散在公共卫生资料、医学和生活方式科学研究、专业组织、商品服务页面与技术文档、监管信息和专家讨论中，也持续出现在生物科技、健康科技、再生医学及 AI4S 等领域。信息持续变化、质量差异很大，也常混有商业宣传。普通用户的注意力有限，没有必要独自长期追踪、筛选和整理这些全球范围的信息。

长寿信息库是 Congtie 为此建立的通用信息基础。它持续承担：

```text
获取
→ 筛选
→ 整理
→ 证据判断
→ AI 初审
→ 人工审核
→ 发布
→ 更新或废弃
```

这个过程把分散信息变成可重复调用、可追溯和有使用边界的信息资产。它不表示 Congtie 已覆盖全球全部信息、消除了所有盲区，或保证每条内容永远正确和最新。

按照当前架构，长寿信息库包括：

- **Knowledge**：相对稳定、可复用的概念和解释；
- **Action Resources**：商品、服务、设备、工具、检测和补剂等信息资源，受 R0/R1/R2/R3 权限控制；
- **Progress and Viewpoints / 进展与观点**：基础研究、临床研究、生物科技、AI4S、产品研发、监管和专家观点；
- **Education**：面向用户的教育文章、指南、术语和 checklist；
- **Governance**：证据、来源、安全、商业边界、版本和审核流程；
- **Invalid or Harmful Information**：已经证伪、有害、过时或被过度宣传的信息，用于帮助避免误导。

长寿信息库不是一次性完成的静态百科。长期方向是持续进行 source monitoring、topic selection、AI-assisted drafting、AI review、human review、publishing、update 和 deprecation。当前 v0 仍以人工触发和 AI 辅助为主，并没有宣称已经实现全自动全球监测。

它同时面向人类和 Agents。随着产品能力完善，人类可通过 Web、H5、小程序、App、搜索、内容页以及 Congtie 对话等方式查询、阅读和使用；Agents 可通过 retrieval 及未来的 CLI、API、MCP、A2A 等接口调用。这些是架构方向，不表示所有接口在 v0 当前都已上线。当前条目本身也没有开启 runtime 或 retrieval。

## 3. 两个信息库的边界

Congtie 区分两个信息基础：

```text
Longevity Information Library / 长寿信息库
= general, reusable longevity context
= 关于“长寿世界”的通用上下文

User Health Information Library / 用户健康信息库
= private, user-specific, permission-gated health context
= 关于“这个用户”的个人健康上下文
```

例如，长寿信息库可以保存 ApoB 是什么、什么是肌酸、某项 GLP-1 研究，以及某个检测设备的证据和边界。用户自己的 ApoB 数值、体检报告、WHOOP 睡眠记录、目标和行动历史则只能属于用户健康信息库。

用户个人健康信息不得进入长寿信息库。长寿信息库与用户健康信息库只有在用户授权、证据、安全和运行时治理边界内，才可共同支持个性化解释与行动支持：

```text
model
+
harness
+
Longevity Information Library
+
User Health Information Library
=
personalized explanation and safe action support
```

这是产品与架构心智，不是医学公式。

## 4. Intervention Coverage Boundary

长寿信息库 v0 可以覆盖补剂、长寿研究中讨论的药物、实验性干预和高风险长寿技术。覆盖这些用户关心的话题，有助于教育、解释证据、说明不确定性、追踪研究进展和提高风险认知。

覆盖不等于推荐。Congtie v0 不得仅基于长寿信息库直接：

- 判断某个用户是否应该使用某种药物或补剂；
- 建议开始、停止或调整药物；
- 提供个体化剂量、加载期、周期、组合或 supplement protocol；
- 推荐实验性或高风险干预；
- 生成治疗方案或临床决策。

未来版本如提供更具体的个人化支持，需要新的用户健康信息上下文、安全规则、证据治理、明确授权及产品审核；这同样适用于药物和高风险干预。

## 5. Commercial Boundary

长寿信息库遵循 `zero_commission_v0`。其中出现商品或服务信息，不等于广告、购买要求或 Congtie 背书；收录、解释和排序不由商业佣金决定，相关商业关系应公开透明。Congtie 当前商业原则是不收礼、零佣金、零广告、零赞助，用户订阅费是葱铁的唯一收入来源。Congtie 不是以广告、赞助或商品交易转化为目标的网店；商品服务信息的呈现必须服从证据、适配、安全和商业透明规则。

## 7. Safety Boundary

本条目不得用于：

- 把长寿信息库描述为医疗数据库、临床决策系统或自动推荐引擎；
- 声称内容全球全覆盖、绝对正确、没有盲区或永不过时；
- 把未来接口或自动监测方向描述为 v0 已上线能力；
- 将用户个人健康信息写入长寿信息库条目；
- 声称 Congtie v0 已获准把研究、补剂、药物或高风险干预的信息覆盖直接转化为诊断、治疗、药物管理、剂量、个性化方案或临床建议；
- 用佣金、隐藏商业关系或购买转化影响收录和排序。

## 8. Agent Usage Notes

在 Founder 批准并通过独立发布流程后，Agent 可使用本条目解释长寿信息库的定位、信息层、持续更新方式、双信息库边界，以及为什么部分信息可以被教育性覆盖、解释和比较，但并不自动构成个性化推荐。

Agent 必须区分当前实现与未来方向，不得声称尚未上线的接口或自动监测能力。Agent 也不得把通用长寿信息与个人健康信息上下文的结合，转化为未经授权或未经治理的个性化诊断、治疗或其他医疗内容。

当前状态为 `human_review_pending`，等待 Founder 第二轮审核，不得进入 runtime 或 retrieval。

## 9. Founder / Reviewer Notes

Founder 需要重点审核：

- “通用长寿信息外脑”是否准确、自然且不过度营销；
- 获取到更新/废弃的长期流程是否清楚区分当前能力与未来能力；
- 五个信息层及 invalid/harmful 内容说明是否与 architecture 一致；
- 与用户健康信息库的 general/private 边界和示例是否准确；
- 补剂、药物与高风险干预的“覆盖不等于推荐”边界是否充分；
- `E5 / product_policy`、`founder_curated` 和 `is_clinical_sensitive: true` 是否适合本条。

本条目尚未批准、尚未发布、尚未进入 runtime 或 retrieval。
